# posts 테이블 - tags, images 컬럼 설계 근거

## 결론

`tags`, `images`는 단순 문자열 배열이며, **포스트 단위로만 읽고 쓴다.** 별도 테이블로 분리할 이유가 없으므로 JSONB로 관리한다.

## 왜 별도 테이블이 아닌가

별도 테이블로 분리하면:
- 포스트 조회 시 매번 JOIN 필요
- 배열 순서 보장을 위한 `order` 컬럼 추가 필요
- 이미지/태그를 독립적으로 조회하는 요구사항이 없음

tags와 images는 항상 포스트와 함께 읽히고, 크기도 작다(태그 수십 개, 이미지 최대 20개). JOIN 비용이 더 손해다.

## PostgreSQL에서 JSONB가 괜찮은 이유

PostgreSQL은 JSONB를 일급 타입으로 지원한다. 단순 문자열 저장이 아니라 바이너리로 파싱해서 저장하기 때문에, 읽을 때 파싱 비용이 없고 인덱스도 걸 수 있다.

| | JSON | JSONB |
|---|---|---|
| 저장 | 텍스트 원문 보존 | 바이너리 파싱 후 저장 |
| 읽기 | 매번 파싱 | 파싱 완료 상태로 저장 → 빠름 |
| 인덱스 | 불가 | GIN 인덱스 가능 |
| 연산자 | 제한적 | `@>`, `?`, `#>>` 등 풍부 |

예를 들어 태그 검색이 필요해지면 별도 작업 없이 바로 쓸 수 있다:

```sql
-- "플로깅" 태그가 포함된 포스트 조회
SELECT * FROM posts WHERE tags @> '["플로깅"]';

-- GIN 인덱스 추가로 대용량에서도 빠르게
CREATE INDEX ON posts USING GIN (tags);
```

이 유연성 덕분에 요구사항이 변해도 스키마 변경 없이 대응 가능하다.

## 다른 RDB와의 비교

MySQL/MariaDB도 JSON 타입을 지원하지만 내부적으로 텍스트 기반이며 인덱스 지원이 제한적이다. Oracle은 21c부터 네이티브 JSON을 지원하지만 PostgreSQL만큼 연산자가 풍부하지 않다. PostgreSQL의 JSONB는 RDB 중 JSON 처리가 가장 성숙한 구현으로 평가받는다.
